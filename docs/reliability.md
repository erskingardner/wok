# Reliability validation

CI is a regression gate. Passing it demonstrates the tested contracts on the
recorded platforms, not exhaustive NIP conformance, absence of vulnerabilities,
or production capacity.

## Gates

| Workflow | Evidence |
| --- | --- |
| `ci.yml` | Formatting, Clippy, all workspace tests (including benchmark correctness), Rust 1.85 compilation |
| `ci.yml` migration job | Builds pinned strfry `9acdaeb1f63919184ece5f2dd67af21f1ed62f1b`; verifies import, event identity, and actual CLI migration |
| `platforms.yml` | Native release build, version check, storage/transport/compatibility/CLI tests on Linux x86-64/ARM64 and macOS Intel/Apple Silicon |
| `fuzz.yml` | 10,000 AddressSanitizer ingress fuzz iterations, protocol-shaped seeds, 2 MiB input ceiling, corpus reuse, crash artifacts |
| `reliability.yml` | Three-minute Linux canary on relevant master pushes/PRs; one-hour weekly or manual soak; retained workload, resource samples, correctness and failure evidence |
| `security.yml` | Dependency advisories, licenses, sources, and dependency policy |

C++ comparisons remain optional locally. Set `WOK_REQUIRE_STRFRY=1` to make a
missing reference binary fail; the migration job always does this. A passing
ordinary workspace run on a machine without strfry does not count as C++
compatibility evidence. C++ is an import/identity reference, not the authority
for behavior that intentionally differs from pinned NIPs.

Fuzzing is triggered by any crate/fuzz change, dependency manifests/locks, or
the fuzz workflow. Inputs are seeded at protocol and WebSocket length boundaries
and retained between runs. This remains a bounded fuzz smoke test; iteration
counts and exercised branches are not coverage of every possible input.

The GitHub ruleset is separate from workflow configuration. Defining mandatory
jobs within a workflow does not make passing checks a prerequisite for pushing
to master. Branch-rule changes require a separate repository-policy decision.

## Generated lifecycle tests

`crates/wok-compat/tests/lifecycle_model.rs` runs four seeded, 40-operation
sequences against real WebSocket and framed Unix connections, with multiple
query and negentropy workers. A guaranteed operation prefix is followed by
randomized ordering. The independent expected-set model consumes signed JSON;
it does not call Wok's filter or visibility implementation.

Operations cover public and restricted publication, replaceable events,
deletions, multiple authenticated identities, reconnects, event/author bans and
restoration, and expiration. After operations, readers compare exact historical
payloads, COUNT results, and reconciled ID sets. Live events are checked for
unauthorized delivery, alteration, duplication, and omission.

Dedicated cases also cover stale AUTH proofs after reconnect and invalidation
of an open sync session after AUTH, read-policy changes, deletion, moderation,
or expiration. A revoked session must not resume. These tests follow Wok's
explicit first-recipient privacy policy; they do not introduce a new NIP rule.
Wall-clock expiration is exercised with bounded waits. Test failure output
contains the seed and operation trace; the sequence is seeded, while AUTH
challenges and expiration timestamps are generated by the live system.

```sh
cargo test -p wok-compat --test lifecycle_model --locked -- --nocapture
cargo test -p wok-cli --test shutdown --locked
WOK_REQUIRE_STRFRY=1 cargo test -p wok-cli --test migration_cpp --locked
```

The CLI tests launch the real binary. The shutdown test publishes an event,
waits for its exact successful receipt, sends SIGTERM with a connection still
open, checks clean exit/socket cleanup, and verifies storage after reopening.
The migration test uses a real C++ database, checks the source data file and
configuration remain unchanged, compares event fingerprints and full JSON, and
inspects the promoted database read-only so writable-open initialization cannot
hide missing tables.

## Controlled Linux soak

Build the relay and separate load driver, then choose a new output directory:

```sh
cargo build --release --locked -p wok-cli --bin wok
cargo build --release --locked -p wok-compat --example reliability_soak
python3 scripts/reliability-soak.py \
  --wok target/release/wok \
  --driver target/release/examples/reliability_soak \
  --seconds 3600 --seed 4242 --out /tmp/wok-soak-run-1
```

Python 3.11+ and Linux `/proc` are required. The runner creates disposable storage
and loopback listeners, never resets an existing database, and refuses to reuse
an output directory. `--port` defaults to 17777. The driver uses both transports
against one relay process and runs approximately one mixed round per second.

The workload includes:

- 20,000 seeded initial notes, followed by a bounded rotating set of 256 notes,
  64 addressable replaceable events, and four deletion events.
- Eight publisher connections, four fast live subscribers, two slow subscribers,
  and periodic reconnects.
- Exact per-event receipts and fast-subscriber payload checks.
- Historical queries and COUNT on both transports every 15 rounds, followed by
  multi-round negentropy against the full expected set.
- Separate 512 KiB ephemeral bursts to pressure slow subscribers without growing
  the durable dataset. Slow-reader closure must be observed in runs of at least
  three minutes.
- A midpoint SIGTERM shutdown, offline integrity check, restart, and exact
  post-restart history verification; final integrity after shutdown.

Each run records hashes of the relay, driver, config and initial signed corpus;
Linux/cgroup details; per-process RSS, anonymous memory, CPU time, thread count,
and database size sampled every five seconds; raw metrics; latency distributions; process logs; and final
results. Keys are seeded; the initial corpus records its actual timestamps and signatures.
Mixed-workload events use the live clock and are not retained as a complete
replay stream, so a seed alone does not reproduce every event byte.

Sampled budgets are 768 MiB relay RSS and 512 MiB database size. Five-second
sampling can miss shorter resource spikes; these are not continuous peak measurements. For each process lifetime,
after 120 seconds of warmup, growth between the first and last six anonymous-RSS
samples must remain within 64 MiB. Short canaries may have no eligible growth
window because of the midpoint restart; they still enforce absolute budgets.
CPU and latency are reported, with bounded operation deadlines, rather than
using shared-runner throughput as a stable performance threshold. Request
latency includes writer delay; no separate writer-queue stall metric is claimed.

The config allows a 30,000-event query and 16 MiB per-connection outbound queue
for this dataset. Rate limiting is disabled to isolate storage/transport
reliability; admission-limit behavior is covered separately by integration tests.
Fixtures retain the host's inherited file-descriptor limit (`nofiles = 0`).
Normal synchronous LMDB durability is retained. The resource cap does not cover
the load driver's memory; container limits and host details are recorded.

This workload checks periodic sync during continuing relay operation. It does
not establish behavior for every large private sync, sustained saturation,
multi-host network faults, disk power loss, or a continuous multi-hour sync
session. Container results are labeled as such and are not bare-metal capacity
claims. Longer campaigns and production observation remain complementary.
